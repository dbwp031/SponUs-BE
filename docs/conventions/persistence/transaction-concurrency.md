# 트랜잭션과 동시성

상태: Draft

## 목적

멀티 인스턴스 환경에서도 도메인 불변식이 깨지지 않도록 트랜잭션, 낙관적 락, 유일성 제약, 중복 명령 처리 규칙을 정의한다.

## 트랜잭션 경계

- Command 유스케이스의 Application Service에 트랜잭션을 둔다.
- Query 유스케이스에는 `readOnly = true`를 사용한다.
- 하나의 업무 결과로 함께 확정되어야 하는 변경은 한 트랜잭션에서 성공하거나 실패한다.
- Domain 객체가 트랜잭션 Annotation을 소유하지 않는다.
- Controller가 트랜잭션을 시작하지 않는다.

원자성이 필요한 예:

- 지원서 최종 제출과 공고 Snapshot 저장
- 협의 시작과 SponsorshipCase 단일 생성
- 합의서 승인과 협찬 확정
- 도메인 상태 변경과 Outbox 기록

## 외부 호출

- S3, Google, 이메일 등 네트워크 호출을 DB 트랜잭션 안에서 장시간 수행하지 않는다.
- 외부 부수 효과는 커밋 이후 Event로 처리하는 것을 우선한다.
- 외부 호출 결과가 도메인 변경의 선행 조건이면 호출과 저장의 실패 정책을 명시한다.

## 낙관적 락

- 변경 가능한 Aggregate Root에 `@Version`을 적용한다.
- 기술 필드명은 `lockVersion`을 사용한다.
- 낙관적 락 충돌은 `409 Conflict`, `E0002`로 변환한다.
- 서버는 충돌한 Command를 자동 재시도하지 않는다.
- 클라이언트 `expectedVersion`은 초기 범위에서 사용하지 않는다.

`@Version`은 겹쳐 실행된 트랜잭션을 보호하지만, 오래된 화면이 나중에 보낸 전체 PUT까지 탐지하지는 못한다. 해당 문제가 실제로 발생하면 `expectedVersion` 또는 ETag 도입을 검토한다.

## 업무 버전과 락 버전

- `lockVersion`은 동시성 제어를 위한 기술 값이다.
- 합의서 revision과 결과 이력은 사용자에게 의미가 있는 업무 버전이다.
- 두 값을 같은 컬럼이나 개념으로 사용하지 않는다.
- 승인된 업무 버전은 불변으로 보존한다.

## 중복 명령

- 초기에는 범용 `Idempotency-Key` 헤더와 요청 결과 저장 테이블을 사용하지 않는다.
- 프런트엔드는 처리 중 버튼을 비활성화한다.
- 서버는 현재 상태를 다시 검증한다.
- DB Unique Constraint가 최종 중복 생성을 막는다.
- 동일 Command가 반복되어도 동일 업무 결과가 두 번 생성되지 않아야 한다.

필수 Unique Constraint:

```text
(club_organization_id, announcement_id)
(origin_type, origin_id)
```

- 첫 번째 제약은 같은 공고 재지원을 차단한다.
- 두 번째 제약은 하나의 지원 또는 제안에서 Case가 중복 생성되는 것을 막는다.

## 비관적 락

비관적 락은 기본값으로 사용하지 않는다. 충돌 빈도가 실제로 높고 짧은 임계 구역에서만 낙관적 락으로 처리하기 어려운 문제가 확인될 때 도입한다.

## 멀티 인스턴스

- Java `synchronized`, 인스턴스 로컬 Lock, 메모리 Set으로 업무 유일성을 보장하지 않는다.
- 정합성 규칙은 공유 DB의 트랜잭션, 락, 제약조건으로 보장한다.
- 분산 Lock은 DB 제약으로 해결할 수 없는 유스케이스에서만 도입한다.

## 금지 사항

- 예외 발생 후 성공 응답 반환
- Unique Constraint 없이 애플리케이션의 사전 `exists` 조회만 사용
- 낙관적 락 충돌 자동 재시도
- 외부 API 호출을 포함한 긴 DB 트랜잭션
- 인스턴스 로컬 Lock으로 멀티 인스턴스 정합성 보장
- 모든 조회에 비관적 락 적용

## 테스트 기준

- 동일 공고 동시 지원에서 하나만 성공하는지 검증한다.
- 동일 origin의 Case 동시 생성을 검증한다.
- 동일 Aggregate 동시 상태 전환에서 하나가 `409`인지 검증한다.
- 상태 변경과 Outbox 저장의 원자성을 검증한다.

## 미결정 사항

- 중복 Command의 응답을 항상 `409`로 할지 현재 상태를 성공으로 반환할지
- 오래된 화면 PUT을 막기 위한 ETag 또는 `expectedVersion` 도입 시점
- 비관적 락 도입을 판단할 충돌률과 성능 기준
